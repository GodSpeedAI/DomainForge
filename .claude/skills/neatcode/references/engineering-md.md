# `engineering.md` — the portable engineering profile

Loaded when reading, writing, or reconciling the project artifact.

`engineering.md` sits at the repository root and records what a competent engineer would need
a week to work out: what the system is, what holds it together, who owns what, what has been
tried, and what is known to be broken. It is the file the next agent reads first.

**It is written on request, never automatically.** `neatcode study` produces it when the user
asks. The default flow reads it and may propose amendments; it does not silently rewrite it.

---

## The provenance rule

The single most important property of this file: **every substantive entry is tagged with how
it is known.**

| Tag | Means |
| --- | --- |
| `explicit` | Stated in the repository — an ADR, a README, an instruction file, a comment. Cite it. |
| `observed` | Read off the code directly. Verifiable now by inspection. Say how. |
| `inferred` | A reasonable conclusion from patterns, not directly stated or provable. Treat as a hypothesis. |
| `disputed` | Two sources conflict, or the documentation and the code disagree. Record both sides. |
| `unknown` | A question that matters and has no answer yet. Recording the gap is the value. |

Without provenance this file becomes an authoritative hallucination: a document that reads
like ground truth, is partly guesswork, and gets more confident each time it is copied. An
`inferred` entry that a later agent verifies gets promoted to `observed`. That is the file
working as designed.

Format entries as `**Claim** — text `⟨tag⟩`` with a citation where one exists:

```markdown
- Domain layer must not import infrastructure `explicit` — `AGENTS.md:31`, `docs/adr/0002.md`
- Enforced by `test/architecture.test.ts:14` `observed`
- Rule is violated in 6 of 14 domain files `observed` — see `src/domain/order.ts:12`
- Verdict: **nominal** — claimed and unenforced in practice `observed`
```

## Structure

Include a section only when there is something real to say. An empty section is worse than an
absent one; a file of headings with "TBD" under each is exactly the documentation theatre this
skill reports as a finding.

```markdown
# Engineering profile — <project>

_Generated by NeatCode study on <date> at <commit>. Entries are tagged
`explicit` / `observed` / `inferred` / `disputed` / `unknown`._

## System purpose
What it does and for whom, in three sentences.

## Architecture
### Claimed
Quoted claims with citations.
### Observed
What the structure and imports actually express.
### Conformance
conformant | partially conformant | nominal | contradictory | unverifiable |
coherent emergent alternative — with the evidence that decided it.

## Architectural invariants
Properties that must hold for the system to remain coherent. What breaks if each is violated.

## Authority map
For each significant invariant or piece of state: who owns it, and where. This is the section
that prevents the most expensive class of future defect.

| Invariant / state | Owner | Enforced at |
| --- | --- | --- |

## Dependency rules
Which modules may depend on which, and how (or whether) it is enforced.

## Domain vocabulary
Terms with precise meanings in this codebase, especially ones that differ from their ordinary
sense. Include the ones that are *ambiguous* — that is where bugs live.

## Boundary rules
Where translation happens, what may not cross, which types are confined to which modules.

## State model
What state exists, where it lives, transaction and ordering guarantees, how transitions occur.

## Error philosophy
How failure is represented and propagated. What is retryable. What fails closed.

## Concurrency assumptions
Threading and async model, what is shared, what is protected, what may be reordered.

## Testing contract
What the project considers proof. Test taxonomy, what is mocked and what is not, coverage
expectations, and how to run each suite.

## Observability expectations
What is logged, what is measured, correlation mechanism, what an operator can answer.

## Security constraints
Trust boundaries, authorization model, secret handling, validated-input conventions.

## Accepted patterns
Structures that are earned here, with the constraint that earns each. This section stops
future runs from re-litigating settled decisions.

## Prohibited patterns
What has been tried and rejected, and why. More valuable than the accepted list — it records
lessons that would otherwise be re-learned.

## Generated vs source
Which paths are generated, by what, and what regenerates them.

## Verification commands
The repository-native checks, what each proves, and how long each takes.

## Known debt
Real, named, with location and consequence. Not aspirational cleanup; things a maintainer
should know before touching the area.

## Contradictions
Where documentation and code disagree, or where the code disagrees with itself.

## Unknowns
Questions that matter and are unanswered. Each with what would answer it.
```

## Writing it

- **Cite.** `path:line` for anything `explicit` or `observed`. An uncited claim is `inferred`
  at best.
- **Record the commit.** The file describes a snapshot; without the sha nobody can tell how
  stale it is.
- **Prefer specific over complete.** Ten cited, accurate entries beat forty plausible ones. The
  failure mode is a document that is comprehensive and 30% wrong.
- **Never invent a rule the repository does not have.** If dependency direction is
  inconsistent, the honest entry is *"no consistent rule `observed`; imports run both
  directions between `domain/` and `infra/`"* — not a rule you think would be good.
- **Distinguish invariant from convention from residue.** The most valuable distinction in the
  file. See [`verbs/study.md`](verbs/study.md).
- **Keep it under a length a person will read.** Beyond roughly 400 lines, split the deep
  material into `docs/` and keep this as the index.

## Reading it

Read it first, and trust it proportionally:

- `explicit` and `observed` entries — rely on them, but spot-check anything load-bearing for
  the current change. Repositories move.
- `inferred` entries — **verify before relying.** They are hypotheses with good manners.
- `disputed` and `unknown` — treat as open questions. If your change resolves one, say so.
- Anything contradicted by what you read today — that is a finding. Report the drift and
  propose the amendment.

## Reconciling it

When the file and the repository disagree, the repository wins on facts; the file may still
win on *intent*. Distinguish:

- **The file is stale** — the code moved. Update the file.
- **The code drifted** — the rule is real and unenforced. That is a finding against the code,
  and probably a missing architecture test.
- **The file was wrong** — an `inferred` entry that inspection now falsifies. Correct it and
  retag.

Amendments are proposed in the report and applied only on request, with one exception: a
`study` run the user asked for writes the file. Never silently rewrite a file a human wrote.

## Relationship to other instruction files

`engineering.md` **describes**; `AGENTS.md` **directs**. If a rule should change agent
behaviour, it belongs in `AGENTS.md`, and `engineering.md` cites it as `explicit`. Keeping the
two separate is what stops the profile from becoming a second, competing rulebook — and
NeatCode reads `engineering.md` as evidence, exactly like the rest of the repository. See
[`untrusted-input.md`](untrusted-input.md).
